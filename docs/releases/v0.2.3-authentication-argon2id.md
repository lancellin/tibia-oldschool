# Relatório técnico da release v0.2.3

## Autenticação Argon2id assíncrona e migração transparente de SHA-1

Data da preparação: 12 de agosto de 2026

Branch de publicação: `main`

Base anterior: `ad428679e100fe492ab39ce04fc8b4ae6a51a645` (`v0.2.2`)

Tag planejada: `v0.2.3`

## 1. Resumo executivo

Esta release substitui a autenticação síncrona baseada exclusivamente em SHA-1
por um subsistema assíncrono dedicado, compatível com hashes Argon2id no formato
PHC e capaz de migrar contas legadas de forma transparente e segura.

Os dois fluxos do protocolo 7.72 foram preservados:

- `ProtocolLogin`: account number + password -> lista de personagens;
- `ProtocolGame`: account number + password + personagem -> entrada no mundo.

Consultas de autenticação, consultas de banimento, verificação de senha,
geração Argon2id, lazy migration e rehash não executam mais no Dispatcher. O
novo `AuthenticationManager` possui workers próprios e fila limitada, sem
compartilhar threads com `PlayerIOManager` ou com o `player_io_service`.

O schema de `accounts.password` foi ampliado de `CHAR(40)` para
`VARCHAR(255) NOT NULL`. `accounts.secret` não foi alterado e continua reservado
para uma futura fase de TOTP/2FA. TOTP e sessão entre login/game ficaram
deliberadamente fora desta release.

## 2. Escopo e decisões de produto

- Algoritmo moderno: Argon2id, versão 19.
- Biblioteca C++: `libargon2`, sem implementação criptográfica própria.
- Representação: PHC encoded autodescritivo.
- Compatibilidade legada: hashes SHA-1 existentes continuam autenticando e são
  migrados somente após uma senha correta.
- Website futuro: deve ler e escrever diretamente o mesmo PHC em MariaDB, sem
  RPC para o TFS.
- Protocolo e OTClient 7.72: nenhuma mudança de wire protocol.
- `accounts.secret`: preservado integralmente.
- Account Manager Lua: não foi adaptado nem removido nesta release por decisão
  explícita do proprietário do projeto; ele será deletado separadamente.
- Não foram implementados TOTP/2FA, emissão de sessão, mudança no cliente ou
  política obrigatória de complexidade de senha.

## 3. Auditoria da arquitetura anterior

O working tree foi reindexado antes e depois das alterações com o Codebase
Memory. O grafo final possuía 63.808 nós e 317.044 relações.

### 3.1 ProtocolLogin antes da mudança

Fluxo encontrado:

```text
thread de rede
  ProtocolLogin::onRecvFirstMessage
      -> g_dispatcher.addTask(ProtocolLogin::getCharacterList)

Dispatcher
  ProtocolLogin::getCharacterList
      -> IOLoginData::loginserverAuthentication
          -> consulta MariaDB
          -> transformToSHA1(password)
          -> consulta da lista de personagens
      -> serialização da lista
```

Consequência: DB e SHA-1 eram executados no Dispatcher.

### 3.2 ProtocolGame antes da mudança

Fluxo encontrado:

```text
thread de rede
  ProtocolGame::onRecvFirstMessage
      -> IOLoginData::gameworldAuthentication
          -> consulta MariaDB
          -> transformToSHA1(password)
          -> ownership do personagem
      -> g_dispatcher.addTask(ProtocolGame::login)

Dispatcher
  ProtocolGame::login
      -> reserva do login
      -> PlayerIOManager::enqueueLogin

worker Player I/O
  materialização do snapshot do personagem

Dispatcher
  aplicação do resultado imutável no estado do jogo
```

O carregamento do personagem já era assíncrono, mas a autenticação de senha
ainda ocorria na thread de rede antes de chegar ao Dispatcher.

## 4. Engenharia comparativa

### Canary

O Canary oferece precedentes úteis para `VARCHAR(255)`, dependência Argon2 e
aceitação transitória de SHA-1/Argon2. Entretanto, a implementação observada em
`src/security/argon.cpp` extrai salt/hash do encoded e recalcula com
`argon2id_hash_raw` usando parâmetros globais de configuração. Essa abordagem
não foi copiada porque enfraquece a propriedade autodescritiva do PHC. Também
foi evitado registrar o hash completo em falhas de autenticação.

Referências:

- <https://github.com/opentibiabr/canary/blob/main/src/account/account.cpp>

### OpenTibiaBR login-server

O código analisado ainda autentica contas com SHA-1. A ideia futura de emitir um
token aleatório e persistir somente seu hash é útil para a próxima fase de
sessão, mas não foi trazida para esta release.

Referência:

- <https://github.com/opentibiabr/login-server/blob/main/src/database/account.go>

### MyAAC

O MyAAC analisado usa um helper de hashing configurável e comparações ligadas ao
legado do ecossistema OT. Para interoperar corretamente, criação de conta,
login, troca e recuperação de senha precisam ser coordenados para usar as APIs
Argon2id do PHP e o contrato de lazy migration/CAS descrito neste relatório.
Não é compatível diretamente sem essa mudança.

Referência:

- <https://github.com/slawkens/myaac/blob/main/system/functions.php>

ZnoteAAC não foi analisado nesta etapa.

## 5. Contrato criptográfico

### 5.1 Policy padrão

| Propriedade | Valor |
|---|---:|
| Variante | Argon2id |
| Versão | 19 (`0x13`) |
| Memory cost | 65.536 KiB |
| Time cost | 3 |
| Parallelism | 1 |
| Salt | 16 bytes via CSPRNG |
| Hash | 32 bytes |
| Armazenamento | PHC encoded em `VARCHAR(255)` |

Exemplo de formato, sem representar uma credencial real:

```text
$argon2id$v=19$m=65536,t=3,p=1$<salt-base64>$<hash-base64>
```

O código usa `argon2id_hash_encoded` e `argon2id_verify` do `libargon2`. O salt
é produzido por `CryptoPP::AutoSeededRandomPool`; o RNG de gameplay não é usado.

### 5.2 Classificação estrita

O valor persistido é classificado nesta ordem:

1. PHC Argon2id v19 sintática e semanticamente válido -> moderno;
2. exatamente 40 caracteres hexadecimais -> SHA-1 legado;
3. qualquer outro formato -> inválido e fail closed.

Além da sintaxe, o parser limita PHCs hostis antes da verificação:

- memória máxima: 262.144 KiB;
- time cost máximo: 10;
- parallelism máximo: 8;
- salt entre 8 e 64 bytes;
- hash entre 16 e 64 bytes.

### 5.3 Limite de senha

A senha permanece case-sensitive e aceita de 1 a 77 bytes. O limite comum foi
derivado do menor payload RSA exato entre os dois fluxos do protocolo:

```text
1 + 16 + 1 + 4 + 2 + 25 + 2 + 77 = 128 bytes
```

O website deve aplicar o mesmo limite em bytes para evitar truncamento ou uma
senha criada no site que não possa ser reapresentada pelo cliente 7.72.

## 6. Lazy migration, rehash e proteção contra corrida

Fluxo de uma conta SHA-1:

```text
ler password antigo
  -> validar SHA1(password apresentado)
  -> gerar PHC Argon2id fora de qualquer lock do banco
  -> UPDATE accounts
       SET password = novo_phc
       WHERE id = account_id
         AND password = valor_lido
```

O update é compare-and-swap. Se afetar zero linhas, o servidor relê o password
atual e valida novamente a senha apresentada:

- se ainda for válida, a autenticação pode continuar;
- se o website ou outro ator mudou a senha para um valor incompatível, a
  autenticação falha e o TFS não sobrescreve o novo valor.

O mesmo mecanismo executa `needsRehash`: um PHC válido com parâmetros abaixo da
policy atual é recalculado depois da autenticação correta e substituído por CAS.
Não há lock de banco mantido durante Argon2.

## 7. Arquitetura assíncrona implementada

Fluxo comum após a mudança:

```text
thread de rede
  ProtocolLogin/ProtocolGame::onRecvFirstMessage
      -> AuthenticationRequest
      -> AuthenticationManager::enqueue

pool AuthenticationManager
  workerMain
      -> IP ban lookup
      -> account/password lookup
      -> Argon2 ou SHA-1 legado
      -> lazy migration/rehash CAS
      -> lista ou ownership do personagem
      -> account ban/namelock quando aplicável
      -> AuthenticationResult imutável

Dispatcher
  callback de conclusão
      -> resposta da character list; ou
      -> ProtocolGame::login
          -> PlayerIOManager::enqueueLogin
```

Propriedades operacionais:

- 2 workers por padrão;
- fila de 64 pedidos por padrão;
- configuração validada com máximo de 8 workers e 4.096 pedidos;
- nenhuma thread é criada por login;
- nenhuma fila é ilimitada;
- nenhuma thread de logout/save executa Argon2;
- não existe fallback de autenticação para o Dispatcher;
- a indisponibilidade usa resposta pública genérica;
- retries transitórios de DB são limitados nos workers de auth;
- shutdown interrompe admissão, limpa senhas ainda enfileiradas e faz join dos
  workers antes de finalizar Player I/O;
- buffers de senha são sobrescritos após o processamento.

## 8. Banco, schema e migrations

Alteração de schema em instalações novas:

```sql
password VARCHAR(255) NOT NULL
```

A migration `40.lua`, nos espelhos source e runtime, altera somente o tipo da
coluna e preserva integralmente os hashes existentes. Pela convenção do TFS,
aplicar o arquivo 40 avança `db_version` de 40 para 41.

Estado observado após o teste no banco local:

- `db_version = 41`;
- `accounts.password = VARCHAR(255) NOT NULL`;
- `accounts.secret = CHAR(16) NULL`, sem alteração;
- 1.014 contas no total;
- 66 contas migradas para PHC Argon2id pelos testes progressivos;
- 948 contas SHA-1 preservadas para lazy migration;
- zero passwords em formato inválido.

Essa distribuição é efeito real dos testes no banco local, não uma migration em
massa. Nenhuma senha foi convertida sem autenticação correta.

## 9. Interoperabilidade com website

A interoperabilidade foi exercitada nas duas direções com senha artificial:

1. C++/libargon2 gerou PHC e o backend independente Python `argon2-cffi`
   verificou com sucesso;
2. o backend Python gerou PHC e o verificador C++ confirmou com sucesso.

PHP não estava instalado no ambiente de teste, mas o contrato equivalente está
documentado em `docs/authentication.md` usando:

- `password_hash(..., PASSWORD_ARGON2ID, options)`;
- `password_verify(...)`;
- `password_needs_rehash(...)`.

Criação, troca e reset de senha no site devem sempre produzir PHC Argon2id.
Login web deve aceitar o PHC moderno e, durante a transição, reconhecer SHA-1
estritamente para aplicar a mesma migração protegida por CAS.

## 12. Caminhos de senha e Account Manager

A busca final por escritores SHA-1 de password encontrou apenas:

- `server/data/globalevents/scripts/startup.lua`;
- `server/data/npc/scripts/account_clerk.lua`.

Ambos pertencem ao Account Manager legado. Conforme decisão explícita do
proprietário, esses arquivos não foram alterados porque o subsistema será
deletado. Enquanto ainda estiverem fisicamente presentes, não devem ser
habilitados ou tratados como caminho suportado de criação/troca de password.

Os usos restantes de SHA-1 em `tools.cpp`, `game.cpp`, `configmanager.cpp` e na
migration 11 são relacionados a HMAC/MOTD e não escrevem senhas de contas.

## 13. Segurança operacional

- Senha não é gravada em logs, métricas, CSV, journal ou saves duráveis.
- Hash completo também não é incluído nos logs de CAS ou falha.
- Erros públicos continuam genéricos para reduzir enumeração de contas.
- Exceções inesperadas no pool não registram textos que possam carregar
  credenciais/verificadores.
- O utilitário de carga usa `MYSQL_PWD` apenas durante a chamada do cliente e
  restaura imediatamente o valor anterior do ambiente.
- Artefatos temporários de interoperabilidade foram removidos após os testes.
- O primeiro resultado headless que continha a senha artificial no summary foi
  apagado; a ferramenta corrigida grava `<redacted>`.

## 14. Riscos e pendências reais

1. As 948 contas SHA-1 continuam legadas até um login correto. Isso é esperado
   pela estratégia lazy e deve ser acompanhado operacionalmente.
2. O website definitivo precisa implementar o contrato completo, especialmente
   CAS na migração/rehash e limite de 77 bytes.
3. MyAAC não é plug-and-play com esta policy; seus quatro fluxos de password
   precisam ser adaptados em conjunto.
4. `argon2.dll` é dependência runtime e deve acompanhar qualquer pacote novo do
   servidor.
5. A policy custa 64 MiB por hash ativo; aumentar workers exige recalcular o
   orçamento de memória.
6. Os dois scripts do Account Manager ainda contêm escritores SHA-1 até a
   remoção separada planejada.
7. O warning C4242 preexistente em `protocolgame.cpp` não foi tratado por estar
   fora do escopo.

TOTP/2FA e sessões entre ProtocolLogin/ProtocolGame não são pendências desta
release; são fases futuras deliberadas.

## 15. Guia para o agente auditor

Recomenda-se revisar prioritariamente:

1. `PasswordHasher::classify`, parser PHC, limites de custo e uso das APIs
   encoded do libargon2;
2. caminhos de limpeza de `AuthenticationRequest::password`, incluindo fila
   recusada e shutdown;
3. `AuthenticationService::authenticate`, affected rows, reload e revalidação
   depois de CAS zero;
4. ausência de DB/Argon2 nos callbacks de Dispatcher de ProtocolLogin e
   ProtocolGame;
5. interação entre `AuthenticationManager::shutdown`, `Game::shutdown` e o
   lifecycle de `PlayerIOManager`;
6. semântica das novas variantes de ban lookup durante indisponibilidade;
7. limite de retries do MariaDB ser local aos workers de autenticação;
8. consistência entre schema/migration source e runtime;
9. CMake, vcxproj e empacotamento de `argon2.dll`;
10. writers de password fora do C++, observando a decisão explícita sobre o
    Account Manager;
11. compatibilidade do limite de 77 bytes com qualquer website futuro;
12. reprodução do CTest, ProtocolLogin, ProtocolGame, outage e shutdown sob
    burst.
